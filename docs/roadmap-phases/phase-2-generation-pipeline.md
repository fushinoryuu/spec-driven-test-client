# Phase 2: Generation Pipeline

The core selling point: a repeatable, one-command path from OpenAPI specs to typed clients. When this phase is done, adding or updating a service means changing a spec file and running one script.

## Goals

- One command regenerates every service client from the specs.
- The generator version is pinned, so output is the same on every machine.
- Stale or hand-edited generated code is caught automatically.
- Adding a service needs no changes to generation scripts.

## Deliverables

| Deliverable | Location |
|---|---|
| Generator config | `openapitools.json` |
| Generation script | `scripts/generate.ts` |
| Drift check script | `scripts/check-generated.ts` |
| Generated clients | `src/generated/<service>/` |
| Pipeline unit tests | `tests/unit/pipeline/` |
| Pipeline doc with a diagram | `docs/generation-pipeline.md` |
| Template overrides (optional, only if justified) | `templates/<generator>/` and `templates/README.md` |

## How it works

```
specs/<service>.yaml
        |
   validate spec
        |
   openapi-generator-cli generate   (pinned Java jar, via npm wrapper or Docker)
        |
   src/generated/<service>/         (typescript-fetch output, never hand-edited)
        |
   format + add "generated" header + typecheck
```

The npm wrapper `@openapitools/openapi-generator-cli` downloads the jar and runs it, so the command line looks the same on every operating system. Its `openapitools.json` file holds a `generator-cli` block with the pinned `version`, an optional `useDocker` flag, and named `generators` entries (each with `generatorName`, `output`, a `glob` for the input specs, and `additionalProperties`). Running `generate` with no arguments runs every configured generator, and `--generator-key` runs a subset. Commit `openapitools.json` so everyone uses the same version.

## Tasks

### 1. Install and pin

- [ ] Add `@openapitools/openapi-generator-cli` as a dev dependency.
- [ ] Run it once so it records the generator version in `openapitools.json`, or set the version explicitly. Pin to the current stable release at the time you build this.
- [ ] Commit `openapitools.json`.
- [ ] Document the Java 11+ requirement and the Docker alternative (from Phase 0).

### 2. Configure the generator per service

- [ ] One `generators` entry with a `glob` over `specs/*.yaml` and an `output` path that includes the spec name, so each service lands in `src/generated/<service>/`. Confirm the placeholder behavior in the docs while setting this up (the documented placeholders include `#{cwd}`, `#{name}`, and `#{ext}`).
- [ ] Set `additionalProperties` from the Phase 0 spike (for example `useSingleRequestParameter`, `supportsES6`, and `importFileExtension` for ESM). Record each choice and why in the decision record.
- [ ] Check how the generator handles the Storefront specs' `apiKey` security scheme and the required `Idempotency-Key` header on `createOrder` (header parameters should appear as request fields). For the Phase 3 stretch goal, also check what the generator produces for a bearer (`http`) security scheme in a small test spec.
- [ ] If the glob approach is awkward, fall back to one named entry per service, generated by a small script that scans `specs/`.
- [ ] Add a `.openapi-generator-ignore` for files you never want overwritten or emitted (for example the generated package.json or README).

### 3. The generate script

`npm run generate` should do these steps in order and stop at the first failure:

- [ ] **Validate** each spec with the generator's `validate` command (or Spectral) and fail with a readable message.
- [ ] **Clean** each service's output folder first, so deleted operations disappear instead of leaving stale files.
- [ ] **Generate** with the pinned version.
- [ ] **Post-process:** run the formatter, and prepend a "generated, do not edit" header if the generator does not add one.
- [ ] **Typecheck** the generated code so a broken generation fails here, not later in someone's test.
- [ ] Print a short summary: services generated, operations per service, generator version.

Support `npm run generate -- --service orders-service` for a single service.

### 4. The drift check

`npm run generate:check` regenerates into a temporary folder and compares with the committed output.

- [ ] Fails with a clear diff summary when committed output is stale or hand-edited.
- [ ] Uses the same generator version, options, and template folder as `generate`, so a stale or edited template shows up as drift.
- [ ] Is used by CI (Phase 5) and as a pre-push hook if wanted.
- [ ] Ignores harmless differences such as line endings.

### 5. Multi-service support

- [ ] Generate all three Storefront specs (customers, orders, shipping) and confirm that adding a service requires only dropping its spec into `specs/` and rerunning `generate`. Name spec files `<service>-service.yaml` (for example `orders-service.yaml`), which becomes the facade name (`ordersService`).
- [ ] Check that the three services do not collide on model or class names. All three specs share an error schema and a `version` tag (so a `VersionApi` class), so expect collisions. Decide on per-service naming (a model and API name prefix, or a package option) and record it. Do this early, because it changes every generated import.

### 6. Pipeline tests

- [ ] **Determinism:** run generation twice, assert identical output.
- [ ] **Compiles:** the generated code passes `tsc` under the repo's strict settings.
- [ ] **Surface check:** for each Storefront spec, assert that the expected operations exist (for example `getVersion` on all three, plus `createCustomer`, `createOrder`, `getShipment`) by importing the generated module.
- [ ] **Removal:** remove an operation from a copy of the spec and assert it disappears from the output.
- [ ] **Invalid spec:** a malformed spec fails with a useful error and does not touch existing output.
- [ ] Keep these fast by using tiny specs under `tests/fixtures/specs/`.

### 7. Custom templates (optional, default is none)

OpenAPI Generator builds its output from Mustache templates (`.mustache` files). Each generator ships a default set, for example for the API classes, the models, and the fetch runtime. You can override any of them by pointing the generator at a template folder that contains only the files you want to change, and the rest fall back to the defaults. The default decision for this project is **no overrides**.

**Decision rule.** Work down this list and stop at the first step that solves the problem:

1. **Generator options** (`additionalProperties`): naming, ES module settings, single request parameter, and similar.
2. **The facade** (Phase 3): call shape, grouping, and ergonomics.
3. **Transport hooks** (Phase 3): headers, auth, logging, retries, timeouts, and error wrapping, through the runtime's custom fetch and middleware support.
4. **The spec** (in the backend project): names, tags, `operationId` values, and schema shapes are often better fixed at the source.
5. **Templates**, only when the change must apply inside every generated file or class and none of the above can do it (for example, a different base error type thrown by every operation, or a header comment convention the generator cannot produce).

Do not use templates for things the facade can do, for one-off tweaks, or as a substitute for regex post-processing. Record in the decision record what was tried at steps 1 to 4 and why it was not enough.

If you do need an override:

- [ ] Export the default templates for the pinned generator version into a scratch folder using the generator's `author template` command, only to read them. Do not commit the whole default set.
- [ ] Create `templates/<generator>/` containing only the overridden files, using the same file names as the defaults.
- [ ] Point generation at that folder through the generator's template directory option (`--template-dir` on the CLI). Check how the npm wrapper config passes it, and set it in `scripts/generate.ts`.
- [ ] Keep each override minimal. Put a comment at the top of each file saying what changed, why, and which generator version it was based on.
- [ ] Keep `templates/README.md` listing every override and its reason. Aim for three overrides or fewer.
- [ ] Add a pipeline test that asserts the behavior the override creates (for example, that every generated API file contains the expected header or error type). The drift check covers the rest.
- [ ] Mustache is logic-less: variables (`{{name}}`), sections that loop or test a value (`{{#items}}...{{/items}}`), and inverted sections (`{{^items}}...{{/items}}`). To see which variables a template can use, run the generator with its debug flags that print the template data (look up the `debugOperations` and `debugModels` options for your version).

**Upgrade procedure** (document it in `docs/generation-pipeline.md`): when you bump the generator version, export the default templates for both the old and new versions, diff them, merge the relevant changes into each override, regenerate, and review the generated diff in its own pull request.

**If your old project had templates:** compare the filenames with the defaults to see what was overridden. Treat the contents as work product and do not copy them. Write fresh overrides only if the rule above says you need them.

## Acceptance criteria

- `npm run generate` produces typed clients for all three Storefront specs, with no manual steps and no name collisions.
- `npm run generate:check` passes on a clean tree and fails after editing a generated file.
- Pipeline tests pass in CI.
- Upgrading the generator version is a one-line change plus a regenerate, and the diff is reviewable.

## Risks and notes

- **Generator upgrades change output.** A pinned version avoids surprise diffs. Upgrade deliberately, in its own PR, and read the diff.
- **Name collisions across services.** Two specs with a model called `Error` can clash. Decide the naming strategy early.
- **Slow CI from the Java startup.** Cache the downloaded jar between runs, or use the Docker image.
- **Hand edits creep in.** The drift check and the "generated" header exist to stop this. Treat any need to edit generated code as a signal to change generator options, the facade, or (as a last resort) templates instead.
